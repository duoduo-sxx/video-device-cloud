# 投见 AdLens · 跨平台广告数据分析平台

> 把 6 个投放平台的数据汇成一本账，用模型算清楚**「谁是我的目标用户、钱花在哪最值、下一步该改什么」**，并把优化动作下发回平台、回收效果。
>
> 纯前端演示项目：**零后端、零网络请求、数据全部本地 mock 但严格自洽**，可一条命令打包成 Windows 便携版桌面应用。

---

## 一、为什么是这个产品

投放团队的真实状态是：巨量、腾讯、快手、百度、小红书、B 站六个后台各有一套口径，日报靠人肉汇总；想知道「这波转化到底来自哪类人」只能靠猜；发现 CPA 涨了，也说不出是素材疲劳、定向跑偏还是落地页变慢。

AdLens 的定位不是「再做一个数据看板」，而是把下面这条链路做成产品：

```
数据接入 → 数据质量 → 数仓加工 → 模型分析 → 人群洞察 → 异常诊断 → 优化建议 → 下发执行 → 效果回收
```

**核心在数据处理**：所有页面上的数字都不是写死的文案，而是同一份日粒度明细逐层聚合、逐层校验出来的结果。任何一个页面改了数字，上下游会对不上——这在设计上是不允许发生的（见第五节「数据勾稽」）。

## 二、业务主流程（9 步闭环）

| # | 环节 | 做的事 | 对应页面 |
|---|---|---|---|
| 1 | **数据接入** | 6 个平台、12 个广告账户授权管理；每日 08:00 增量拉取，失败自动重试，记录数据水位线 | 投放账户 / 同步任务 |
| 2 | **数据质量** | 10 条校验规则（完整性、唯一性、及时性、一致性、有效性），命中行数与影响行数可下钻 | 数据质量 |
| 3 | **数仓加工** | ODS（原始）→ DWD（清洗、口径统一、去重）→ DWS（主题汇总）→ ADS（分析结果），21 张表带血缘 | 数仓分层 / 指标字典 |
| 4 | **模型分析** | 5 种归因模型、6 维人群 TGI、7 级转化漏斗、素材 7 日衰减、计划边际 ROI | 归因分析 / 转化漏斗 / 计划与素材 |
| 5 | **人群洞察** | 回答「谁是这个广告的目标用户」：六维画像 + TGI + 相似人群包 + 结论卡 | 人群洞察 |
| 6 | **异常诊断** | 环比越阈值 → 自动下钻 4 层根因链 → 给出结论与置信度 | 异常诊断 |
| 7 | **优化建议** | 五要素建议：问题、数据依据、建议动作、预估影响、置信度 | 优化建议 |
| 8 | **下发执行** | 采纳 → 审批 → 生成变更单 → 调平台接口改预算/出价/素材/落地页 | 预算分配 / 变更单 |
| 9 | **效果回收** | 生效后 7 日对比实际转化、CPA、ROI，闭环验证建议是否真的有效 | 变更单（效果回收列） |

导航按这条链路分组：**投放总览 → 数据接入 → 数据资产 → 模型分析 → 优化执行 → 报表与设置**，左侧菜单从上到下就是业务流向。

## 五、数据勾稽：为什么每个数字都对得上

这是本项目最核心的设计约束。**任何一处改动都会破坏上下游一致性，因此所有金额与计数只能由下往上聚合，不能反向编造。**

### 5.1 六条硬约束（`npm run verify` 逐条断言）

1. **账户汇总 = 平台汇总**：`Σ 账户指标 = 平台指标`（金额按分、计数按整数）
2. **平台汇总 = 大盘汇总**：6 个平台相加严格等于总览页的大盘数字
3. **计划汇总 = 账户汇总**：`splitAccountMetrics` 用**最大余数法**把账户月汇总拆到计划，保证 `Σ计划 === 账户` 且无 0.01 尾差
4. **创意汇总 = 计划汇总**：同上，逐计划拆分到创意
5. **素材指标 = Σ 使用该素材的创意**（素材可能跨计划被复用，因此素材消耗 ≥ 任一单计划）
6. **归因恒等**：5 个归因模型的总转化完全相等（权重以千分比定义、合计 1000‰，再用最大余数法分配），只在平台间分配上有差异；并额外断言 `Σ平台 = 总转化`
7. **人群占比合计 = 100%**：每个维度（性别/年龄/城市/兴趣/设备/时段）的转化占比、消耗占比、大盘基准占比，各自合计为 1（千分比定义，容差 0.002）

> 派生指标（CTR、CPC、CVR、CPA、ROI、AOV、CPM、频次、支付率）只能通过 `src/lib/metrics.ts` 计算，页面里不允许出现硬编码的结果值。

### 5.2 三处「真实事故」，让异常诊断有据可依

数据里预置了三类真实场景，异常诊断页、质检页、同步页、建议页的文案与数字全部由它们推导：

| 事故 | 位置 | 表现 | 触发页面 |
|---|---|---|---|
| 素材疲劳 + 加预算 | ACC-102（巨量·效果）10/28 起 | 消耗 ×1.18、CVR ×0.62 → CPA 明显上涨 | 异常诊断「成本上涨」、素材疲劳表、建议 SG-002 |
| 主计划审核不通过 | ACC-301（磁力）10/26 起 | 掉量 30%、CTR ×0.88 | 异常诊断「掉量」、建议 SG-003、变更单 CH-20261028-001 |
| 授权过期断流 | ACC-501（小红书）10/29 起 | 之后 3 天无数据 | 同步任务失败、质检「及时性」未通过、账户状态 auth_expired |
| 落地页换版 | ACC-201（腾讯）10/24 起 | CVR ×1.22 | 变更单 CH-20261029-006 的 7 日效果回收 |

### 5.3 其他保证真实感的手段

- **日历节奏**：国庆出行高峰 ×1.28、节后蓄水 ×0.88、双 11 预热从 1.05 逐日爬坡到 1.42、周末 ×1.14 —— 所以趋势图上有真实的波峰波谷，而不是随机噪声
- **确定性伪随机**：所有抖动由 `hash(账户-日期)` 生成，刷新页面、切换页面数字完全一致，演示不会「跳数」
- **双向引用完整**：异常 → 建议 → 变更单 → 效果回收；质检 → 数仓表 → 血缘上下游；同步任务 → 账户状态，全部 ID 可互查，无孤儿数据
- **样例数据取自演示数据本身**：数仓表详情里的样例行不是随便编的，而是从当前账期的计划、素材、漏斗、人群结果中生成

### 5.4 自检脚本

```bash
npm run check     # = typecheck + verify + smoke
npm run typecheck # tsc --noEmit
npm run verify    # 4597 条数据勾稽断言 + 打印大盘概览
npm run smoke     # 16 个页面 SSR 渲染冒烟，确保无运行期崩溃
```

`npm run verify` 覆盖：账户→平台→大盘逐层求和、计划/创意/素材拆分、归因跨模型恒等、人群占比 100%、漏斗逐级递减、对账差异率反算、账户状态与数据一致性、行级合理性（点击 ≤ 曝光、转化 ≤ 点击、支付 ≤ 转化）、跨表引用完整性。

## 六、技术栈与目录

- **React 18 + TypeScript(strict) + Vite 5 + Tailwind 3**
- 路由 `HashRouter`（打包成桌面端后可直接 `file://` 打开）、状态 `Zustand`、图表 `Recharts`、图标 `lucide-react`
- 无 UI 框架依赖，组件全部自建，贴合 B 端高密度信息展示

```
src/
├─ types/index.ts          # 领域模型 + 中文枚举标签（平台/账户/计划/指标/异常/建议/变更单…）
```

### Windows 便携版（项目内**不引入** electron 依赖）

`electron/main.cjs` 只是一个加载器（`contextIsolation: true`、`nodeIntegration: false`、`sandbox: true`、外链交给系统浏览器），Electron 运行时由 `electron-builder` 在打包时按 `-c.electronVersion` 下载。

```bat
set "ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/"
set "NPM_CONFIG_ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/"
set "ELECTRON_BUILDER_BINARIES_MIRROR=https://npmmirror.com/mirrors/electron-builder-binaries/"
npm install
npm run build
for /f "delims=" %i in ('npm view electron version') do set "ELECTRON_VERSION=%i"
set "PACK_OUTPUT=release-retry-%RANDOM%"
npx --yes electron-builder@latest --win portable --x64 --config electron-builder.yml -c.electronVersion=%ELECTRON_VERSION% -c.directories.output=%PACK_OUTPUT%
```

产物：`%PACK_OUTPUT%\AdLens-1.0.0-portable-x64.exe`，双击即用，无需安装。

### GitHub Actions 自动打包
`.github/workflows/build-windows-portable.yml`：推送到 `yunshu-platform` 分支或手动 `workflow_dispatch` 触发，`windows-latest` 上跑 `npm install → npm run build → electron-builder`（已内置三个国内镜像环境变量），产物上传为 artifact `AdLens-portable-win-x64`。

## 九、边界与后续

- 本项目为**演示版**：数据为本地 mock，无后端、无网络请求；接入真实平台只需把 `src/mocks/*` 换成 API 适配层，聚合与校验逻辑（`src/lib/metrics.ts` + `scripts/verify.ts`）可直接复用。
- 归因模型为权重分配的可解释实现（末触/首触/线性/时间衰减/数据驱动），不含真实 Shapley 计算与增量实验。
- 预算模拟采用弹性系数近似，未考虑平台侧的竞价环境变化。
- 权限为前端模拟，真实环境需服务端鉴权。
