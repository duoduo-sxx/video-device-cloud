# 设计说明

## 1. 整体思路

这是一套「运维 + 数据工程」双视角的企业级后台。设计上的三个取舍：

1. **信息密度优先于留白**。目标用户每天盯同一个界面 8 小时，表格行高 44px、字号 13px、卡片内边距 20px，比大留白的消费级设计更实用。
2. **状态色语义化**。任务、节点、链路、告警、审批五类对象的状态色全部收在 `constants/dict.ts`，页面只引用 `StatusTag`，保证同一状态在任何页面颜色一致。
3. **数据先于图表**。所有图表都由真实结构的 Mock 数据驱动（32 个任务的状态分布、14 条链路的 RTT/丢包），而不是写死的假数组，所以切换筛选、推进进度后图表会真的变化。

## 2. 页面结构逻辑

```
总览（看我今天要不要加班）
  └─ 传输任务（我该做什么）
       └─ 任务详情（为什么慢/为什么失败）
  └─ 链路与节点（基础设施好不好）
       └─ 拓扑（整体长什么样）
  └─ 优化引擎（为什么快 / 省了多少钱）
  └─ 告警（哪里出事了）
  └─ 审批（我要批什么）
  └─ 系统管理（谁能用）
```

导航按「监控 → 操作 → 分析 → 治理」排列，符合运维人员的排障动线：先看总览，再看告警，再下钻到任务/节点。

## 3. 图表取舍

| 图表 | 用在哪 | 为什么 |
|---|---|---|
| 面积图 | 24h 吞吐趋势 | 强调「量」随时间的累积感，双系列区分上行/下行 |
| 环形图 | 任务状态分布 | 比饼图更省空间，中心可放总数 |
| 横向条形 | 链路 Top5 / 部门排行 | 类目名较长时横向可读性远好于纵向 |
| 堆叠柱 | 分片执行情况 | 同时表达总量与构成（完成/传输中/失败） |
| 散点矩阵 | 链路质量 | 两个连续维度 + 一个尺寸维度，比表格更能看出异常簇 |
| 热力图 | 时段利用率 / 任务密度 | 找「规律」而非「数值」，日历式布局最直观 |
| 漏斗 | 任务阶段 | 表达转化与流失，适合汇报 |
| 桑基图 | 数据流向 | 表达多对多的流向与占比，一张图替代三张饼图 |
| 雷达图 | 优化能力对比 | 六维能力启用前后对比，适合做「收益」叙事 |

**刻意不用地图**：节点分布若用中国地图，涉及审图号合规问题；改用「区域卡片 + 抽象拓扑」既规避风险，也更贴合「网络拓扑」而非「地理位置」的语义。

## 4. 关键交互

- **任务进度**：全局 5 秒 tick，仅推进 `running` 状态任务，进度、已传字节、速率、ETA 联动；到 100% 自动转 `success` 并写入 `finishedAt`。这让演示时页面"活着"。
- **新建向导**：右侧摘要卡使用 `Form.useWatch` 实时跟随，不依赖 "下一步" 才更新，减少填写时的心理负担。
- **危险操作**：删除任务要求输入 `DELETE`，避免误触；审批驳回要求填写原因且至少 4 字。
- **角色切换**：顶栏可实时切换三种角色，`AuthGuard` 直接不渲染写按钮（而非 disabled），便于演示权限差异。
- **筛选反馈**：列表顶部固定统计条（共 N 个 / 运行中 / 排队 / 失败），筛选后数字同步变化。

## 5. 数据设计

- 使用 mulberry32 固定种子生成随机数，保证每次刷新数据一致（便于截图与演示对齐）。
- 时间统一基于 `2026-10-19`，相对时间由 dayjs 计算，避免"写死成 3 分钟前"。
- 数值全部落在真实业务区间：任务 12GB–4.8TB、速率 120–980 MB/s、RTT 8–68ms、健康分 62–99.6，杜绝"2TB 3 秒传完"这类失真数据。
- 状态写入 localStorage，但会校验 `seedDay`；跨天后自动重置，防止「3 天前的任务仍显示进行中」。

## 6. 桌面封装预留

- `base: './'` + HashRouter，`dist/index.html` 双击可用。
- 无 Service Worker、无外链 CDN、无远程字体与图片（头像为首字母色块，图标为组件）。
- 图表、字体、图片全部本地化，断网可用。
